# ADR-0001: 多相性の解決を X-Macro によるコンパイル時コード生成で行う

- **状態:** 採用（帰結のうち「`default:` を置かない」は [ADR-0011](./0011-default-label-and-trap.md)、「網羅性がビルドフラグに依存しない」は [ADR-0018](./0018-exhaustiveness-by-arity.md) が訂正）
- **関連:** [G-001](../GUARANTEES.md#g-001), [G-002](../GUARANTEES.md#g-002), [G-004](../GUARANTEES.md#g-004), [C-01](../constraints.md#c-01), [C-12](../constraints.md#c-12)

## 文脈

C にはパラメトリック多相がない。「任意個・任意型の直和型」を汎用的に扱うには、
多相性の解決をどの段階で行うかを決める必要がある。

## 決定

**コンパイル時のコード生成（X-Macro）**で解決する。型リストを1箇所で定義し、
複数の生成マクロがそれを再利用する。

## 検討した代替案

| 方式 | 型安全性 | 実行時コスト | 不採用の理由 |
|---|---|---|---|
| `void*` + 実行時型タグ（type erasure） | コンパイラによる保証なし | heap 確保・キャスト | 直和型の主目的である「コンパイル時に型の区別を保証する」性質そのものを失う |
| 固定バッファ + vtable（`std::variant` 的） | あり | heap 確保なしだが関数ポインタ登録の定型コードが要る | 今回の用途に対して実装コストが見合わない |
| 可変長マクロ（FOR_EACH トリック）で1呼び出し形式にする | あり | なし | 自前のプリプロセッサ再帰トリックか外部ライブラリ（metalang99 等）が必要になり、可読性・デバッグ容易性を損なう |
| **X-Macro（採用）** | あり | なし | 標準 C の範囲で完結し、型リストを複数の生成マクロから再利用でき、エラーメッセージも比較的追いやすい |

## 帰結

**網羅性がビルドフラグに依存しない。** 生成される関数の引数リストは型リストから作られるため、
引数の個数は常に variant 数と一致する。variant を1個足せば必須引数が1個増え、渡し忘れは
`too few arguments to function` という**通常の関数プロトタイプ検査**として落ちる。
`-Wswitch` の運用に依存しない（[G-001](../GUARANTEES.md#g-001)）。

**順序取り違えも検出できる。** 各ハンドラの型は variant ごとのペイロード型で固有になるため、
ペイロード型が異なれば順序を入れ替えると `-Wincompatible-pointer-types` になる
（[G-002](../GUARANTEES.md#g-002)）。ただし `-Werror` の運用が前提で、
2 variant のペイロード型が同一だと検出できない（[C-01](../constraints.md#c-01)）。

**`switch` に `default:` を置かない。** `NAME_tag_t` をマクロ経由以外で拡張された場合に
`-Wswitch` が働くようにするため。不正 tag の検知は `default:` ではなく
別の手段で行う（[ADR-0010](./0010-unhandled-tag-hook.md)）。

**デバッグ容易性を一部犠牲にする。** マクロ定義自体のバグが追いにくく、型リストの構文ミスは
間違えた箇所ではなく `DEFINE_SUM_TYPE(...)` の行にエラーが出る（[C-12](../constraints.md#c-12)）。
